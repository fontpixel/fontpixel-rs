# Macintosh bitmap fonts and fork containers

Implementation basis (consulted 2026-10-04): Apple's [NFNT/FONT resource](https://developer.apple.com/library/archive/documentation/mac/Text/Text-250.html), [font type](https://developer.apple.com/library/archive/documentation/mac/Text/Text-251.html), [extended offsets](https://developer.apple.com/library/archive/documentation/mac/Text/Text-252.html), [FOND](https://developer.apple.com/library/archive/documentation/mac/Text/Text-269.html), [resource fork](https://developer.apple.com/library/archive/documentation/mac/MoreToolbox/MoreToolbox-99.html), Apple's [AppleSingle/AppleDouble developer note](https://nulib.com/library/AppleSingle_AppleDouble.pdf), and the [MacBinary II conference specification](https://files.stairways.com/other/macbinaryii-standard-info.txt).

The independent oracle is monobit 0.54 (MIT, Rob Hagemans; NFNT writer also Kelvin Sherlock). Its structures were consulted; production decoding and encoding are native Rust, with no Python or external process dependency. No GPL implementation is used.

| Wire field | Model interpretation |
|---|---|
| firstChar/lastChar | Inclusive legacy code range; no implicit Unicode conversion |
| kernMax + high width/offset byte | Glyph BBX x |
| low width/offset byte | Horizontal integer advance |
| fRectHeight / descent | Full-height glyph raster, BBX y = -descent |
| ascent/descent/leading | Strike metrics |
| fontType bit 13 | Monospaced versus proportional |
| optional width table | Preserved exact 8.8 words in original NFNT bytes |
| optional height table | Preserved original words; full raster remains authoritative |
| FOND association size/style/ID | Point/pixel size, style, corresponding resource |
| resource names | MacRoman decoded family name; original resource name bytes retained |
| unknown FOND tables/resources | Opaque retained records, never interpreted as executable data |

`owTLoc` is measured in 16-bit words starting at byte 16. Positive `nDescent` supplies its high word; zero/negative values do not. The separate Apple extended-offset page says “beginning of resource”, contradicting the detailed field definition; this implementation uses the field-relative interpretation employed by real resources and monobit.

The reader supports bare big-endian 1/2/4/8-bit NFNT/FONT and resource-fork structures (including data-fork resources `.dfont` and suitcase files), wrapped by MacBinary I/II/III and AppleSingle/Double v1/v2. FONT and NFNT share their raster format. Two/four/eight-bit samples map exactly to Gray8 (sample × 255 / maximum sample). New Gray8 output uses eight-bit NFNT; an explicit threshold requests monochrome output. Indexed RGB color resources use the documented Gray8 projection below; synthetic and Lisa-compressed resources fail explicitly. Reserved flags are retained. Resources have an explicit unknown charset unless the caller supplies one; resource-family script metadata does not justify guessing Unicode. MacRoman labels require explicit interpretation.

Resource and entry ranges, overlap, duplicates, overflow, table boundaries, resource counts, total glyphs and allocations are checked before access/allocation. Additional resources are resolved only through ReadContext. AppleDouble output contains a data asset and its `._` companion in an OutputBundle. New containers have zero timestamps; existing MacBinary header dates are preserved. AppleSingle can hold the resource structure in entry 1 (data fork), as CiderPress2 does, or entry 2 (resource fork); the original choice survives a same-container write. MacBinary with a dfont in its data fork is also supported.

Raw source NFNT data is retained once per strike, enabling exact unchanged-resource output including optional tables and unusual valid padding. Unknown nonfont resources and FOND records are retained at collection level. Edited strikes regenerate their raster tables. A final readback compares source mapping, glyph metrics, names, charset, global metrics and ordered properties field by field; differences receive loss diagnostics. Unsupported mappings receive individual omission diagnostics; an entirely unrepresentable font fails with its accumulated report. Gray8 reduction requires an explicit threshold. Cumulative resource counts include envelopes, forks and explicitly resolved companions. No metadata is silently hidden in a private extension.


The resource map is regenerated, retaining named resources, attributes, IDs and reserved handle fields. Unreferenced zero padding may be normalized; nonzero unreferenced bytes are diagnosed as loss. A mismatching nonzero map-header copy is rejected. Shared exact resource-name strings are legal; partial overlap and shared resource payloads are rejected as ambiguous. FOND optional tables remain opaque source properties: the codec updates font associations, family names and size/style fields, and preserves other table bytes. These are not currently exposed as native kerning or fractional-advance editing APIs.

The default `Container::Dfont` writes a resource structure; `ResourceFork` and `Suitcase` share those bytes. `Bare` requires exactly one strike. `AppleDouble` requires `write_bundle`: the primary asset is the data fork and its sibling `._<name>` contains the AppleDouble header. To read that pair, pass the data asset to `ReadContext` and explicitly select `NfntReadOptions::apple_double_resource`. Reading the `._` file directly also works when it carries the font resource fork. No implicit filesystem lookup occurs.

Legacy glyph positions are limited to the standard byte range. Unicode mappings are not guessed or coerced; convert the charset explicitly first. Advances and relative offsets occupy unsigned bytes; geometry beyond these representation limits is rejected instead of clipped. Unsupported names are encoded with `?` substitutions or truncated to the 255-byte Pascal-string limit, and the readback comparison reports the changed name. Timestamps, absolute paths and process-dependent IDs are not generated.

Indexed color support follows [Apple font-type bits](https://developer.apple.com/library/archive/documentation/mac/Text/Text-251.html), the [ColorTable resource layout](https://developer.apple.com/library/archive/documentation/mac/QuickDraw/QuickDraw-267.html), and [Inside Macintosh V](https://vintageapple.org/inside_o/pdf/Inside_Macintosh_Volume_V_1986.pdf), pp. V-135 and V-183. The `fctb` is a separate resource with the NFNT's resource ID. Its `ctSize` is entry count minus one; color specifications contain an index and three 16-bit RGB components. Image tables use their explicit index; device tables (`ctFlags=0x8000`) use entry position.

Color projection uses each component's most significant byte and computes coverage `255 - ((299*R + 587*G + 114*B + 500)/1000)`. The read report records `palette_to_gray` loss even though original RGB bytes survive as container metadata. Missing entries are ordered by pixel index and filled from white background (coverage zero) to black foreground (coverage 255); a sole missing entry uses background. Choosing these port colors is reported as `palette_port_colors` loss. Unknown palette flags, duplicate explicit indices and indices beyond the font depth are rejected. Only fonts declaring a color table interpret the matching `fctb`; unrelated tables remain opaque. Bare color resources need their resource-fork context. Lisa compression and dynamically synthesized fonts remain explicitly unsupported.

Classic `FONT` resource IDs encode family in bits 7–14 and point size in bits 0–6, as documented by Apple’s [font resource history](https://developer.apple.com/library/archive/documentation/mac/Text/Text-189.html). Size-zero `FONT` resources provide family names and remain opaque collection resources; they are not raster records. With no FOND association the reader derives size and family from those IDs. Newly written FONT resources use family IDs 128–255, size 1–127, and a matching FOND; named families also include the classic size-zero name resource. Original source identities survive roundtrip.

Detection follows bounded container entries to an actual NFNT/FONT bitmap resource. Generic MacBinary or Apple envelope headers alone are insufficient evidence; MacBinary II/III header CRC, fork boundaries, resource map headers/type/reference ranges, and raster location/width/optional-table bounds are checked without creating bitmaps or model records. Bare resources require the documented fontType marker plus valid raster tables. Parsing still validates all resources, metadata, overlaps and budgets. This prevents unrelated sfnt table directories from masquerading as MacBinary headers while retaining classic FONT, color, extended-offset, data-fork and resource-fork variants.
