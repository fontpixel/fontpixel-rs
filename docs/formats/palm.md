# Palm OS font resources and databases

Research recorded before implementation, 2026-10-04.

The primary authority is Palm's [68K API Reference, Fonts](https://palm.wiki/development/docs/601/PalmOSReference/Font.html), especially FontType, FontTypeV2, FontDensityType, and the two resource layouts. The [Programmer's Companion, Text](https://palm.wiki/development/docs/601/PalmOSCompanion/Text.html) describes custom fonts and density selection. The archived Palm [PDB/PRC specification](https://web.archive.org/web/20050212082335/http://www.palmos.com/dev/support/docs/fileformats/PDB+PRCFormat.html) defines the container. MIT monobit 0.54 `apple/palm.py` and `apple/nfnt2.py` are supplementary interoperability references; no GPL or MPL implementation is used.

All standard resource integers are big endian. FontType is thirteen 16-bit words: type, first/last code, maximum width, reserved kern/descent, rectangle width/height, width-table offset, ascent/descent/leading, strip row words. A v1 resource (0x9000) stores strip, location table, then offset/advance table. Locations include the missing-character image and a terminal offset. The width-table anchor is the word at byte 16, not the resource start. Missing slots have 0xffff advance-table entries. Palm ignores kerning offsets; they are retained as source properties instead of applying Macintosh semantics.

V2 (0x9200) adds version 1, density count, and six-byte density records. Locations and advances remain in standard 72-dpi coordinates; bitmap offsets are resource-relative. Each density becomes a model strike. Supported density identifiers are 72, 108, 144, 216 and 288; integer scaling is exact. Where 108-dpi coordinates are fractional, the reader must use an explicitly documented rounding interpretation or reject the ambiguity rather than silently guessing. The writer will require exactly representable standard-coordinate geometry.

PDB record databases have eight-byte entries; PRC resource databases have ten-byte entries and attribute bit 0 set. Names occupy 32 bytes; type/creator occupy bytes 60–67; the first record list begins at 72. Database resource types may be NFNT, nfnt or application-specific names, so validated resource content identifies fonts. Non-font resources and application/sort metadata must be retained or explicitly reported. Chained record lists require cycle/overlap checks. All payload extents are bounded by sorted physical offsets, independently of directory order.

Writer reports cover character domain/range, aliases, missing/default glyph selection, unsupported glyph bearings, grayscale thresholding, cell padding, unrepresented names/metrics/properties, and container changes. Successful output is decoded with the same limits before return. Limits include cumulative glyphs, metadata, reports, resource lists, strips and decoded rasters. The implementation must not materialize whole strips as one byte per pixel.

Independent checks use monobit's Palm/Palm-PRC/NFNT/NFNT2 readers and independently assembled fixtures; monobit has no Palm writer. Native density and container test coverage and any verified limitations are recorded in `reports/w5.4.md`.

The additional afnx profile is an ARM little-endian extended resource: an extra reserved word follows densityCount and density entries are eight bytes (density, reserved word, bitmap offset). FontConv 1.63 documents and emits this profile; monobit independently decodes it.

GrayFont uses the author's `GrayFormat.txt`, revision 1.9, 2003-11-30, distributed in [FontConv 1.63](https://downloads.sourceforge.net/project/palmfontconv/Font%20Converters%20for%20PalmOS%20Dev/1.63/FontConvForPalmOS163full.zip). It specifies GrFn headers (22 bytes for v1, 34 for v2), eight-byte bitmap-resource references, twelve-byte glyph records, and GXYZ resource indexes (16-bit offset and length). GU14/GU34 are upright, GL14/GL34 and GR14/GR34 are rotated variants. Each image is a Palm BitmapTypeV1/V3 at four-bit depth. Pixels map to Gray8 coverage by multiplying the index by 17. Bitmaps may use scanline differential compression; resource offsets are four-byte aligned. GrFn revision low nibbles are backward-compatible by the author's specification. Remap resources (0x4000) contain references rather than independent font pixels and are preserved as opaque database resources.

The GrayFont reader restores rotated glyphs to font coordinates and records the source resource profile. The writer emits upright, four-bit Palm v3 bitmaps and splits resources before 16-bit offsets overflow. Quantization, changed orientation representation, and padding are audited. FontConv executables remain external GPL oracles; no GPL code is copied or translated into the library.

FontConv README documents FontSubst's afnx variant with fontType 0x0200 (little endian), alongside the standard 0x9200. It has the same tables and density records. The reader accepts both; `PalmVersion::FontSubst` selects the variant explicitly. The original converter's `fsconvert` utility is an external validation oracle.

Current behavior: record-list cycles, overlapping directories, duplicate PRC identities, out-of-range tables, duplicate densities and ambiguous fractional coordinates fail before decoding. Existing multi-density database resources retain their grouping on extended-format output. Standard NFNT/nfnt/afnx/GrFn resource tags follow the selected output layout; application-specific tags remain intact. Palm 108-dpi input can opt into floor rounding, which produces a Repair diagnostic. Encoded character values remain legacy codes unless explicitly mapped on output.

The original `fsconvert` utility confirms FontSubst's two-bit change in both directions. Monobit 0.54 has two confirmed interoperability defects: afnx offset/advance bytes are reversed, and ff/ff missing-slot sentinels are multiplied before being tested at high density. Crosschecks assert these differences and use original FontConv for afnx. GrayFont bitmap indexes count unique stored images: FontConv can share one index between multiple characters, despite the format document's range-oriented wording. All six original-tool bitmap profiles, including compressed/rotated images, are tested. Monobit's experimental GrayFont module is not a registered complete reader.

GrayFont output uses GU34, optional lossy four-bit quantization, and explicit per-field audit. A remap-only GrFn resource has no independent pixels; it remains opaque when a database also contains fonts. A database containing only external/remap references cannot form a standalone FontSet and is rejected. No external Palm system resources are silently fetched. FontSubst's four-system-font installation convention is distinct from encoding native resources and is not synthesized automatically.

The author's GrayFormat.txt explicitly restricts GXYZ images to no transparency, no color map, and optional scanline compression. RLE, PackBits, color tables and indirect runtime pointers belong to broader Palm bitmap APIs, not this GrayFont resource profile; they are rejected rather than misinterpreted as grayscale glyphs.
