# Adobe Prebuilt BEPF/LEPF

The historical interface declaration is [Adobe's prebuiltformat.h](https://github.com/johnsonjh/NeXTDPS/blob/master/fonts-21/bin/prebuiltformat.h). It bears a restrictive copyright notice: only publicly observable field facts are used; source declarations/implementation are not transplanted. The [MIT monobit reader](https://github.com/robhagemans/monobit/blob/040b1738085ce7967478499eef2835d2cffc95fd/monobit/storage/fontformats/prebuilt.py) supplies an independent interoperability reference.

Version3 has a16-bit byte-order selector, fixed-width header offsets, counted character names/widths, matrices and masks. Strings are nul-terminated and name data has a declared total size. Each matrix contains six signed16.16 values plus pixel depth. Mask records contain byte dimensions, signed horizontal offsets/advances and an absolute raster pointer. Separate arrays may carry vertical scalable widths and per-mask vertical metrics. All pointer/count products, strings and overlapping spans must be bounded before allocation.

Native readers/writers cover both byte orders, multiple matrices/strikes and monochrome/grayscale masks. Grayscale is represented in Gray8 without silently reducing to ink. Exact fixed-point values and transformation matrices remain properties; nonintegral metric projections and unsupported affine/vertical interpretation must be reported explicitly. Original vertical data must survive when not semantically changed. Character names are native identifiers; automatic Unicode inference is not required. The decoder does not drop unsupported-depth strikes as the independent reader does.

`PrebuiltReadOptions` may require a byte order. `PrebuiltWriteOptions` chooses byte order, optional depth1/2/4/8, charset name and identifier. Gray8 to Mono requires an explicit threshold; reduction to2/4 bits requires exact samples or explicit quantization. Character counts and matrix counts are signed16-bit positive values. A collection must share family and sorted character names and compatible scalable widths; violations fail rather than merging distinct glyphs. Both native device-advance axes are represented. Affine/fractional projection and provisional vertical interpretation emit Loss while exact source vectors remain properties.

The original NeXT `prebuild` producer was compiled externally as32-bit code and run on original BDF fixtures. Its LEPF numeric selector is zero, but a13-pixel Mono row `9688` is stored unchanged; Gray8 samples `00 11 22 77 88 FF` are unchanged. Therefore numeric byte order and pixel order are independent. Both native options expose `bitmap_bit_order: PrebuiltBitOrder`, default MsbFirst. Explicit LsbFirst selects a compatibility profile; no endian-based pixel inference occurs. The producer promotes input depths2/4/8 to8 and thus does not establish a packed2/4-bit producer oracle. Those precisions are covered by independent byte fixtures and the BE reference decoder.

Monobit0.54 incorrectly mirrors LEPF rows; the crosscheck converts numeric fields alone to BE before invoking that reader, leaving raster bytes untouched. Original producer input/output and executable hashes are retained externally in `../local-work/prebuilt-research/pixel-evidence.json`, with a copy linked from the C2 evidence report.
