# Signum! E24, P9, P24 and L30

Primary format documentation: [editor charset](https://sdo.dseiler.eu/formats/eset) and [printer charset](https://sdo.dseiler.eu/formats/pset), by the Signum Document Toolbox author. The toolbox implementation is AGPL and is not copied; monobit's MIT reader is the implementation reference/oracle. Header magic is `eset0001`, `ps090001`, `ps240001` or `ls300001`, followed by a big-endian font type, 128 opaque bytes, a character-buffer size and 127 offsets. The documentation's `0x10`/“128” statement is inconsistent; known values16/128 are accepted and retained, output defaults to128.

Each character buffer record has top, height, width and reserved bytes, then raster data, padded to an even byte count. E24 has fixed sixteen-pixel rows and width denotes advance; printer rows have width bytes. X=0 and y=baseline-top-height. Default baseline/line-height pairs follow observed software conventions: E24 18/24, P9 36/48, P24 58/64, L30 48/52; callers can override them explicitly. Printer advance is the trimmed ink width because there is no declared pixel advance field, and that inference is documented. Raster padding/opaque fields and source bytes remain properties; no unknown kerning is invented.

Native writers support all four variants, reconstruct offsets and word alignment, preserve opaque metadata when representable, and audit all changes. Legacy code positions are not implicitly Unicode. Invalid offset tables, truncated/padded records, oversized fields and excessive aggregate allocations fail. Successful writes are reread under the same limits before output is returned.
