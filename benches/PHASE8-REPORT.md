## 结论与适用范围

> 2026-10-12：兼容层小调用性能修复后的重测见[“兼容层性能修复之后”](#兼容层性能修复之后2026-10-12)；本节及其后各节其余内容为 2026-10-07 的原始结果，保留为历史。

WASM 兼容层在 SC 解析、PCF 写出、批量文字绘图上更快；小型属性、字形和 bitmap 调用通常比纯 JS 慢。
原生 JS API 的批量操作通常更快，但也有 BDF 写出和查字等较慢项目。不能把 Python 阶段的加速比套到 JS。
完整列表、五轮范围和配对比值均列在下面，没有按结果删选用例。

- SC 解析：兼容层配对中位比值 Node 1.62×、Chromium 2.40×。
- SC PCF 写出：兼容层 3.12× / 4.83×，原生 API 12.77× / 22.45×。
- 绘制 2,000 个不同字：兼容层 65.84× / 71.54×，原生 API 120.47× / 121.57×。
- 兼容层 SC BDF 写出：配对中位比值 0.48× / 0.61×；Latin TTF 为 1.20× / 0.90×，跨轮波动明显。
- 兼容层 `Font.length` 仍扫描已编码字形，SC 单次中位数 312 / 344 µs；纯 JS 是 `Map.size`。
  这是算法和跨界成本的差异，不能只归因于 WASM 调用开销。没有为本次测速改默认上限或接口语义。

### 修了什么（Node 中位数，修复前 → 修复后；修复前为本报告 10-07 的原始表）

1. **按编辑版本缓存的投影**（`e6aa634`）：`Font.length` 改读每版本缓存的已编码码点表（原先每次在 Rust
   扫描全部字形）312.181 → 0.048 µs；`getprop()` 的 ASCII 键读缓存的属性投影（原先每次在 Rust 重建整张表并
   JSON 往返）5.482 → 0.217 µs；不带范围的 `itercps()` 复制每版本缓存的顺序 2.691 → 0.116 ms。
2. **headers/props 视图在两次编辑之间不走读 trap**（`c00da7d`）：Proxy 保留（写、删、新键仍立即按顺序进入模型），
   target 镜像投影，读 trap 只在编辑后的第一次读取时装回并刷新。`{...font.headers}` 5.822 → 2.487 µs。
3. **Bitmap 行字符串留在 JS 侧，原生栅格按需创建**（`f23889b`、`8829aa9`；行跨界改为一个字符串，`6d32842`）：
   `new Bitmap(rows)` 4.422 → 0.783 µs，`clone` 1.097 → 0.403，`getpixel` 0.274 → 0.068，
   `todata(0/1/2/3)` 1.615/1.546/6.324/5.576 → 0.286/0.105/2.875/0.634，`todata(4/5)` 按栅格状态记忆
   6.195/6.311 → 0.589/0.542；原生编辑链 `clone().crop/shift/concat/glow` 1.766/1.659/2.521/2.072 →
   1.725/1.210/1.785/1.584。
4. **字形句柄按需创建**（`6d32842`，`dace1b7`）：从字体读到的字形先持有槽位与元数据快照（`lookupSlot`，
   每版本缓存；`iterglyphs` 每 256 个批量读取），只有编辑、绘制等操作才创建 wasm 句柄（`attachSlot` 给出与当时
   `lookup` 完全相同的句柄，编辑后按快照重建，合并语义不变）；没有新报告条目时跳过 `warningsSince`。
   `glyphbycp(65).meta.codepoint` 2.978 → 0.529 µs，`glyphbycp(65).meta` 8.399 → 1.209 µs，
   遍历 Latin 全部字形读 codepoint 25.670 → 2.839 ms；`glyph.draw()` 11.794 → 11.856 µs（未改善，见下）。

### 仍然较慢的调用及原因

配对比值 < 1 且范围不跨 1 的兼容层用例（Node / Chromium）：

- `font_headers`（0.03 / 0.07，多 2.4 / 1.8 µs）：`font.headers` 必须是 Proxy 才能让新增键、删除和赋值立即、
  按顺序写入模型并保持旧有错误时机；V8 对 Proxy 的展开没有快速路径，即使没有读 trap 也比普通对象慢一个数量级。
  单个键读取（`font.headers.fbbx`）已与普通属性读取同级。
- `glyph_draw`（0.27 / 0.46，多 8.8 / 6.4 µs）：耗时在共享 Rust 核心的 `Glyph::draw`（与 Python 相同语义：
  十六进制行逐位转二进制字符串、每次投影全部 headers、再裁剪），以及创建句柄和返回 bitmap。没有为此改共享核心算法。
- `bitmap_construct`（多 0.75 / 0.57 µs）、`bitmap_clone`（0.20 / 0.41）：剩余是 JS 侧的行校验、
  非枚举状态属性和自有 `bindata` 访问器（为保持 `toEqual` 只看到 bdfparser-js 的属性）；pure 只保存数组引用。
- `bitmap_crop`（0.07 / 0.12，多 1.6 / 1.4 µs）、`bitmap_shift`（0.29 / 0.44）、`bitmap_concat`（0.83 / 0.43）：
  这些编辑走原生栅格（复制、编辑、取回行字符串），每次至少两次跨界；pure 直接切字符串。`glow` 反而快 2.3–2.8×。
- `bitmap_todata_2`（0.49 / 0.63）与 Node 的 `todata_1`（0.54，+0.05 µs）：由行字符串构造嵌套数组/复制数组，
  绝对差 ≤ 1.5 µs。
- Node 的 `glyph_metadata`（0.50，+0.63 µs）、`font_property`（0.49，+0.11 µs）、`iterate_glyphs_latin`（0.74）、
  `lookup_A`（0.92）：每个字形对象仍有两个属性定义（非枚举状态、`meta` 访问器）；Chromium 中这四项为
  0.98 / 0.98 / 1.09 / 1.88，接近或快于 pure。
- 整批任务：`write_bdf_sc`（0.40 / 0.57）——兼容层在 Rust 重新生成 5.7 MB 文本再整体解码成 JS 字符串，
  pure 主要拼接已持有的字符串；`write_ttf_latin`（0.98 / 0.99）持平。

已经不慢或更快的：解析（1.7–2.3×）、PCF 写出（3.2–4.8×）、文字绘制（3.2–96×）、`length`、`getprop`、
`itercps`（5.8–12.6×）、`getpixel`（Node 1.03，Chromium 0.77 但范围跨 1）、`todata(0/1/3/4/5)`（Chromium 全部 ≥ 0.94）。

### 对 npm `latest` 的含义

典型 bdfparser-js 用法（载入字体、按码点取字形并读 `meta`、读 headers/props 单个键、`length`/`itercps`、
画整段文字、写 PCF/TTF）在修复后与纯 JS 持平或更快；仍明显更慢的是展开整个 `headers`、单字形 `draw()`、
逐个 bitmap 构造/裁剪/平移这些每次几微秒的调用，以及 SC 级 BDF 写出（约慢 40–60 ms）。

release、fat LTO、`-Oz` 与构建脚本记录的 WASM feature flags；所有正式性能数据均排除 fast 构建。

原始 [phase8-js.json](results/phase8-js.json) 记录包 SHA、输入 SHA、参考源码与 bundle SHA、全部样本和负载。

输入为 TongPixelSans14Large-SC.bdf（5,746,021 B）和 Latin.bdf（418,907 B）。SC 用于解析、
BDF/PCF 写出和文字；Latin 用于 TTF、draw-all 与小型字形调用。draw-all 没有提高默认像素上限。
解析输入和读写用的字体预先准备，时间不含磁盘/网络传输或 WASM 加载。

每个宿主做五轮配对：偶数轮 pure → compat → native，奇数轮反序；Node 每个引擎新进程，
Chromium 每个引擎新 context（该宿主五轮复用一个 browser 进程）。三引擎运行相同的固定次数；
整批任务预热一次，小调用预热 20 次。Node `global.gc()` 与 Chromium CDP GC 在计时外执行。
每次调用都消费返回值到相同的 checksum sink；原生句柄 `free()` 计入调用时间，兼容层遵循引用 API 的 GC 生命周期。
GC 仍可能在计时中自然发生，这也是实际调用成本的一部分。

正确性摘要在计时外检查：pure/compat 每项输出摘要相同，原生读取验证字数、绘图验证像素行，
其余标记为 compare 的原生操作同样与 pure 相同。解析摘要只验证字数，不能代替完整模型测试。
原生三个 writer 的序列化契约与兼容层独立，因此记录 SHA 但没有以 pure 字节作为失败条件；
本次 BDF、PCF 的摘要实际相同，TTF 不同。原生/CLI 逐字节合同由独立的 Node 和三浏览器验收覆盖。

共享桌面没有隔离其他用户负载。引擎开始时 1 分钟 load：Node 3.56–5.63，Chromium 4.49–7.79。
范围是五次实测最小/最大值，不是置信区间。报告采用**同轮 pure 时间 ÷ 被测时间的中位数**；
它不一定等于两列时间中位数的商，范围跨 1 的项目不能据此宣称稳定加速。
所有原始样本保留，不扣除 noop 时间，不做异常值剔除。

表中时间是每次操作的中位数 [最小–最大]。整批单位 ms，小调用单位 µs。
比值 > 1 表示被测接口更快。† 表示 pure 中位数不超过同宿主 pure noop 中位数的五倍；
这些小调用已接近循环/JIT/计时下限，省略精确比值。其他极短调用的比值也应谨慎解读。

### 初始化（预加载字节，ms）

每个模块、每个宿主五个**新进程**，字节在计时前读取/获取。分别测 JS 动态 import、
`WebAssembly.compile(bytes)` 和 `await init(compiledModule)`；总计是该样本三段之和。
各列单独取中位数，因此分项中位数之和不必等于总计中位数。OS 磁盘缓存可能已热。
先完成所有构建，再按五轮旋转/反转组合顺序，逐样本记录负载；这轮测量未并行运行本任务的构建或其他重任务。
宿主是共享桌面，仍不能把不同 profile 的微小差异归因于体积；总时间未必随体积单调变化。
这不是冷下载或首屏时间：WASM/字体字节的 HTTP 传输不计时，浏览器 JS import 列包含本机 loopback
HTTP 模块获取，不能外推真实网络延迟。同步实例化的首轮 gate 246 在 Chromium 主线程
8 MB 限制处失败，保留失败记录；247 改用正常异步 API、不开启限制豁免 flag。

## 限制与后续使用

- full 模块很大；按任务选择支持的 profile、延后加载，并把大输入放在 Worker 中。
  实验 feature 矩阵为体积取舍提供数据，不代替第 9 阶段的网站 profile 设计。
- 这是本机单次五轮 A/B 实验；负载、JIT、GC、时钟粒度会影响尤其是很短的调用。
  不据此承诺其他 CPU、浏览器版本或手机上的时间。
- 三浏览器功能验收包含 57,106 字形拼合期间的主线程 heartbeat；其时长仅用来诊断响应性，
  不混入本表的配对基准，也不把它当作帧率或最坏延迟保证。
- 基准只对列出的任务和输入成立。参考测试的 11 个已说明差异与 2 个未加载的参考构建套件，
  完整原生 API 覆盖、默认资源上限、strict/report 和 portable-float 堆复核，分别见阶段报告。
- 本阶段到此停止；没有开始 fontpixel.com 页面、phase 9 或最终项目报告。
