# W5 scaling review and GPI allocation correction

Reviewed 2026-10-04. This is a source-level scaling review of the named Phase 5
families, not a formal performance run or a claim about every registered codec.
No timing was performed. The initial task was read-only; root subsequently
authorized only `gpi/writer.rs` and `tests/gpi.rs` changes to close finding GPI-1.
Other reviewed production sources and frozen fixtures were not modified.

## GPI-1 — descriptor allocation before its cap and aggregate check (fixed)

The original `gpi/writer.rs:257` allocated `vec![0; 28 + n * cell]` before
charging its bytes at the following line. Here `n` is the inclusive native code
span, not the number of input glyphs; `cell` includes the maximum preserved
`gpi.descriptor_extra` length. Two tiny glyphs at legacy 0 and 65535, with a
65,525-byte extra on one glyph, produce `n = 65536`, ABC `cell = 65535`, and
`definition_len = 4,294,901,788`. The earlier `n * 128` charge is only 8 MiB.
The input fits default model limits while the allocation far exceeds the default
64 MiB output cap. This is an allocation-order defect and sparse-range
amplification, not an ordinary glyph-loop O(N²) diagnosis. The large allocation
was never executed during this review.

The fix at `gpi/writer.rs:163–188` checks stride, multiplication, additions,
complete record cap, and cumulative table budget before output allocation.
The descriptor buffer at `gpi/writer.rs:279` uses fallible exact reservation only
once, then initializes the already checked length. Accepted wire bytes and
native descriptor/raster layout are unchanged.

Two new regressions at `tests/gpi.rs:216` and `:239` cover respectively:

- Two sparse codes, a 65,525-byte descriptor extra, and a 1 MiB output cap:
  return `ResourceLimit { resource: "GPI output record bytes", ... }`. Its error
  precedence checks the table cap rather than the old later aggregate rejection.
- Codes 0/255 and 4,086 extra bytes: the approximately 1 MiB descriptor table
  fits a 2 MiB output cap but must be rejected by the 512 KiB cumulative budget.

Code ordering establishes rejection before reservation; these are functional
budget regressions, not allocator instrumentation or high-memory stress tests.
All seven GPI integration tests and the single-feature Clippy gate passed.
Fuzz build and exact final hashes are recorded in `w5.gpi-budget.*` reports;
root owns the new GPI freeze, formal ASAN campaign, and formal performance run.
B final3 remains the historical snapshot, superseded for GPI by this correction.

## PFR-1 — shared physical record parsing (bounded observation, deferred)

`pfr/wire.rs:350–361` parses a physical record for each logical directory entry.
The format permits repeated `(physical offset, size)` references. The physical
character loop at `:276` processes all C physical characters even if its bitmap
strike contains only one. L logical fonts sharing that record therefore perform
O(L × C + N log C + P) work, where N is the actual output bitmap glyph count and
P the decoded bitmap payload. This becomes quadratic in a jointly increasing
L/C family; it is not a quadratic lookup inside ordinary single-logical fonts.
Different logical fonts also legitimately create separate output fonts.

Three original small files share one logical/physical body and contain one
bitmap per logical font. The existing frozen debug adapter accepted each, with
no read loss and the expected code 1 in every output font:

| Logical fonts L | Shared physical characters C | Input bytes | Output glyphs N | Physical-character visits derived from the loop |
| ---: | ---: | ---: | ---: | ---: |
| 16 | 64 | 628 | 16 | 1024 |
| 32 | 128 | 1092 | 32 | 4096 |
| 64 | 256 | 2020 | 64 | 16384 |

The visit counts are source-derived operation counts, not observed runtime or
hardware counters. Reproduction:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 ../local-work/w5-scaling-review/pfr_shared_witness.py
```

The script independently assembles the shared-reference layout from the
project's original seed definitions; it does not modify those definitions or
invoke a benchmark mode. Each command/exit, fixture hash and adapter hash is in
`../local-work/w5-scaling-review/pfr-shared-result.json`.

Witness script SHA256: `a6f620afe67a45b3ad389f252fb08d02c01e0cb242baaf722fdfc039d87e44fd`.

The native physical character count is u16. `max_resources` bounds logical
fonts and generated strikes (default 1024); `max_glyphs` bounds each physical
character table and the total generated bitmap glyphs. Every repeated `Char`
allocation is charged before reservation to the shared `max_total_bytes`
(default 256 MiB). Thus this path has an explicit cumulative limit and does not
allocate from an unchecked maximum code value. Source spans and GPS programs
are also checked. A possible future optimization is to cache immutable physical
records by `(offset, size, dialect)`, preserving per-logical loss locations.
Root explicitly deferred that architecture change pending formal PFR results;
this review changes no PFR code and makes no absolute performance claim.

## Reviewed paths without another confirmed scaling defect

Let A be actual aliases, P the visited/decoded bitmap bytes or pixels, S allocated
glyph slots (including tombstones), R an inclusive native 16-bit code span, and
M the number of strikes. These bounds describe the codec logic; image compression
and font model validation add their own bounded passes.

| Family | Checked behavior and limits |
| --- | --- |
| SSFN binary / ASCII | Character and fragment indexes use BTreeMap; skip records advance codepoints without a Unicode-sized array. A fragment boundary is parsed once into the index; glyph composition visits referenced pixels and charges the work before use. Per-glyph canvas/packed buffers and output appends are proportional to payload; `append` uses amortized reservation. No whole-font clone in a glyph loop. Ligatures have a native limited PUA table. |
| PFR | Sorted physical characters use binary search for each bitmap entry. Writer sorts actual glyphs with BTreeMap and appends programs once; compression walks each bitmap, not earlier glyphs. The shared-record exception is described above. |
| PC/GEOS | Actual aliases enter a BTreeMap. The native dense descriptor range is capped to 65,535 **bytes** before allocating (`pcgeos/writer.rs:246`), so sparse 16-bit codes cannot create an unbounded range. Every native glyph payload is visited once per output. |
| GPI | Dense R is at most 65,536 mapped slots plus optional null; GPI-1 now bounds R × descriptor stride before allocating. Resource IDs use BTreeSet. LX decoded objects are cached by object index, so several resource slices do not trigger repeated object decompression. Native-preservation decode/comparison and ordinary write/readback add a fixed number of full passes. |
| Prebuilt | Named glyph BTreeMaps are constructed once per strike. Verifying shared names and widths traverses actual N × M glyphs; map lookups are logarithmic. N × M is explicitly budgeted. Raster packing and readback traverse actual payload, with no per-glyph whole-model clone. No codepoint-sized array. |
| RISC OS | Sorted slot maps query 32-code chunks; empty chunks are skipped. Version 8 has at most 2,048 native chunk directory entries, not a Unicode array. The phase grid is bounded to 1/4/16 phases. Reader sorts each bounded chunk's offsets once. IntMetrics applies `edit_glyph` to one glyph at a time; that clones the current glyph, not the font. |
| VLW | Sorted actual Unicode keys; one directory pass and one sequential raster span per glyph. High Unicode values do not grow storage. Writer computes the sum of payload sizes before output allocation, then one readback/audit. |
| PILfont | Fixed 256-entry native directory; one atlas decode per font. Writer shelf placement uses a forward pass, not pairwise placement searches, and caps the rectangular atlas before allocation. |
| SFont / RFont | Indexed code selection and monotonically advancing strip scans. RFont's end-of-strip padding scan occurs once per strip, not for every glyph. Native page grouping and shared rectangular atlas dimensions can include padding; that decoded rectangle is capped/charged before allocating. |
| Imageset | Resource paths/codepoints sorted once; each glyph image encoded/decoded once. Assets and the output model accumulate linearly under resource/aggregate limits. Filenames encode sparse values; no array is sized to the highest label. |
| QPF | BTreeMap actual 16-bit codes; range building appends to the last contiguous run. Balanced tree emission uses pending index intervals; no repeated scan of all earlier ranges. Native preservation adds only a fixed full pass. |
| QPF2 | GMap/glyph vectors follow bounded actual native glyph-slot counts (u16), not maximum Unicode. Alias vectors follow glyph IDs; cmap uses real mappings and contiguous groups. Shared `sfnt/cmap.rs` format 4/12 builders traverse actual mappings, including sparse supplementary codepoints. |

The shared model's `add_glyph` indexes only the new glyph; it does not rebuild
the entire cmap. Normal insertion appends increasing glyph IDs in each alias
list. `edit_glyph` clones one glyph and updates that glyph's indexes. Arbitrary
user models with many removed slots still require scanning their existing S
slots; that is not an allocation proportional to the largest character code.

`gem/common.rs::convert_gray` clones the source set at most once per operation,
outside glyph loops, and only if grayscale conversion is needed. The common
audit creates target slot references once. Root's sorted-vector alias membership
fix replaces quadratic alias `.contains` behavior. QPF/QPF2 use the separate
`fbit/common.rs` audit: ordered glyph zip and monotone property iteration; the
inner `.any()` consumes the same iterator and does not restart a full scan.

The PNG sink's `try_reserve_exact` looked suspicious but is not a confirmed
quadratic path with the locked dependency: `image 0.25.10` calls `png 0.18.1`
`write_image_data`, which compresses one image before emitting IDAT chunks of
up to 2,147,483,647 bytes. Under the ordinary 64 MiB cap there is one IDAT,
not one output-buffer reallocation per glyph or scanline. The separate atlas
`image.rs` sink already implements capped geometric growth. No sink was changed.

## Evidence and review limits

Inspection used `rg`, bounded `sed` reads, the existing adapter's three small
PFR `dump` invocations, and the GPI gates authorized after the initial finding.
No full-repository gate, long fuzz campaign or formal timing was launched here.
This is a targeted algorithm/allocation review, not a proof of every malformed
input path or of third-party compressor complexity. Pixel counts, native dense
ranges, multiple requested logical fonts and image rectangle area remain real
input/output costs and are not conflated with glyph count alone.
