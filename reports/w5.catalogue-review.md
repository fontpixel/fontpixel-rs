## Result and evidence

All **99** stable IDs were checked against the **99** `all-formats` feature
entries and their individual `cfg!(feature = id)` gates. Every ID has its format
document; no duplicate ID, duplicate suffix, uppercase suffix, leading dot,
wildcard, comma file-type marker or arbitrary filename was inserted. Catalogue
order and all previously accepted suffixes were preserved. **44** suffix arrays
were expanded and **4** display names corrected.

The baseline is the existing accepted catalogue. New suffixes use
[the survey's canonical monobit inventory and wrappers](w5.1-survey.json),
the individual [format documents](../docs/formats/README.md), and implemented
native variants. Publisher naming evidence additionally comes from the survey's
pinned [Bits'N'Picas README](https://github.com/kreativekorp/bitsnpicas/blob/43b11dca0809a3342b8281b570897e8654ffe705/README.md):
FONTX2 `.ftx`, MGTK `.fnt/.mgf/.mpf`, NFNT `.nfnt`, SFont/RFont `.png`, and
PSF `.psfu.gz`. Qt's cached original makeqpf generator emits `.qpf2`; its native
QPF documentation identifies the legacy format. Processing PFont's original
source calls its image font representation `.vlw`. The SSFN publisher's binary
and ASCII specifications explicitly name `.sfn` and `.asc`; the documented gzip
transport adds `.sfn.gz`. PFR's `.pfr` identifies its bitmap-bearing container,
not an assertion of outline rendering support.

## Name corrections

- `beos`: `BeOS |Be` → `BeOS |Be; bitmap fonts`.
- `gpi`: `OS/2 GPI font resources with FontStart/Metrics/Definition/Kerning/End records, character definition types 1/2/3` → `OS/2 GPI bitmap fonts / NE / LX containers`.
- `symbos`: `SymbOS FNT variable-width bitmap font header and glyph byte offsets.` → `SymbOS small / medium / big bitmap fonts`.
- `playdate`: `Playdate source FNT metrics/kerning plus PNG image table fonts` → `Playdate FNT source / PFT compiled bitmap fonts`.

BeOS's semicolon is part of the native `|Be;` identifier and must not truncate the
human-readable name. The GPI name now includes its implemented NE/LX wrappers;
SymbOS names all three native sizes; Playdate names source and compiled variants.

## Filename policy and deliberate exclusions

- ChiWriter's `.[specx]ft` is expanded only into the finite literal suffixes
  `.sft/.pft/.eft/.cft/.xft`, alongside `.set`; the wildcard is not stored.
- Oberon's literal `.scn.fnt` is a valid compound suffix. Printer `.Pr?.Fnt`
  names use the real generic `.fnt` suffix; no `?` expression is stored.
- TeX DPI-dependent `.*pk/.*gf/.*pxl` patterns are not added literally. Existing
  `.pk/.gf/.pxl` entries remain; `.tfm` is a companion metric file, not these fonts.
- `SYSTEM.FONTS`, `font.lib`, `HZKxx/ASCxx`, `x90y45`, `Font` and `IntMetrics`
  are fixed or conventional native names, not `.fonts/.lib/.hzk/.asc/...` suffixes.
- ZapFont's `,1bd` denotes a RISC OS file type and is not a dot extension. The
  registry's dot-suffix matcher is unchanged; this marker requires a future
  dedicated filename-hint policy if desired.
- PILfont `.pbm` is an atlas companion, and Playdate PNG is an image-table
  companion for this implementation. Neither is advertised as a standalone
  primary font suffix. SFont/RFont PNG, conversely, encodes the font itself.
- Generic raw `.fnt` remains only a hint: the reader still requires an explicit
  layout. HZK and headerless structural ambiguity are not solved by guessing.
- fbit and NFNT share the actual supported Mac envelopes (`.dfont/.suit/.bin/`
  `.as/.adf/.rsrc/.hqx`). Bare NFNT `.f/.nfnt` do not imply bare fbit aliases.
  IIgs `.fon/.bsc/.bsq` reflects its native record and BinSCII transport.
- GPI accepts OS/2 NE/LX modules. The survey's monobit `mzfon` family handles
  Windows and OS/2 FON files (confirmed by its installed package declaration),
  so `.fon/.exe/.dll` are valid container hints for GPI as well as Windows FON.
  The bitmap resource `.fnt` remains a separate native input.

Empty suffix lists remain for HZK, Berkeley vfont, DEC DRCS, BBC VDU 23, BeOS,
Quark Catalyst, +3DOS, RISC OS bitmap files, TasPrint, Wyse and ZapFont. The cited
inventory and documents establish no general dot extension for these entries;
authoring a test file named after its codec would not establish one.

## Registration and capability consistency

`FormatInfo.feature_enabled` means only that its Cargo feature is selected.
`Registration::planned` starts with no hooks, and `FormatStatus` derives actual
read/write/detect values from installed hooks. Those semantics remain intact.
At the review snapshot, 97 IDs had matching public modules and installed
reader/writer registration paths (including existing embedded/vector adapters).
Remaining planned/unregistered entries were `xerox`, `ssfn`. These are active parallel work,
not declared complete by this metadata change. Hook availability is not a claim
that final fuzz/performance acceptance has finished. Root may install them later.
All installer IDs found in `lib.rs` matched catalogue IDs, public module gates
and either dedicated registration methods or the common codec macro.

## Root follow-up

Filename collisions are intentional and must remain explicit. `.fnt` now has
17 candidates, `.fon` includes Windows FON, IIgs, Dr. Halo and OS/2 GPI; `.json`
includes image mappings and BMFont; `.txt` includes hexdraw, Consoleet and psf2txt;
`.png` includes generic image and SFont. Longest-suffix matching still applies.
Any CLI fixture relying on formerly unique suffixes should use an explicit
`--to`/`--from` where appropriate. Do not remove true suffixes to make a test
choose a format by accident. `.sft`, `.pft`, `.exe` and `.dll` can also collide.
No CLI files were edited here. Remaining codec installation/acceptance and any
special handling of fixed filenames or RISC OS comma types stay with root.
