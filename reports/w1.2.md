## Delivered

- Actual feature-gated BDF detector, parser and deterministic writer, wired into
  `fontpixel::registry`, `read`, `write` and the real `FontSet` API
- SPEC-v3/Python header/property/glyph parsing: ASCII whitespace, CR/LF/CRLF,
  initial BOM, UTF-8 replacement, strict signed-32 fields, typed quoted/unquoted
  properties, case and insertion order, comments, recovery and warning text/order
- Complete horizontal/vertical metrics, global defaults, METRICSSET/CONTENTVERSION,
  source charset identity/GL, unencoded alternates, negative raw ENCODING and
  Unicode-tagged non-scalars through signed-32 maximum
- All source duplicate glyphs retained in the core; canonical output/effective
  lookup select the later record. Duplicate properties/headers retain source
  records while canonical writing follows Python's order/value/spelling rules
- Packed pixels plus field-level original hex rows and semantic snapshots.
  Unmodified rows keep exact spelling/padding/row anomalies; modified pixels and
  dimensions are regenerated. No whole-input-file shortcut is stored or used
- Normalized name/metric edits reconciled with original headers/properties;
  direct property edits/deletions are honored when semantic views are unchanged
- Public `source_rows`, `validate_bitmap`, `BdfWriteOptions` and `BdfCodec` APIs;
  explicit Gray8 threshold, unsupported-model-field losses and bounded output
- Shared gzip transport independent of codec registration: bounded multi-member
  decoding, corrupt/truncated/CRC checks, deterministic single-asset `.gz` output.
  BDF enables flate2's pure-Rust backend; no PCF capability is claimed
- CLI `info` produces real text/JSON metadata; `convert` handles input loading,
  combined read/write reports, strict exit 3, gzip and safe same-directory atomic
  output replacement. Errors never truncate an existing destination
- Format mapping/design documents, provenance/license notices, tiny licensed
  fixtures, synthetic oracle generator, property tests, crosscheck scripts,
  Criterion/five-call benchmarks and an actual cargo-fuzz target

### Resource safety

Checks happen before raster expansion/allocation and before retaining a new
glyph. Declared CHARS/property counts never drive an allocation. Primary,
decompressed, total/model, per-line/per-glyph-source-table, actual glyph count,
per-glyph pixels and writer output limits are tested. Required numeric parsing
consumes only the needed tokens, even with a large trailing-token line. Fresh
raster serialization streams rows and does not allocate a height-sized array.
Zero-area dimensions up to the signed-32 source limit do not expand into rows.
The limits are bounded model/result policies, not a process-wide allocator quota.

### Fuzzing

Final-code cargo-fuzz/libFuzzer run: **611 seconds**, **1,425,975 executions**,
**cov 3520 / ft 17243**, active corpus 2,927 inputs / 1,571 KiB, peak reported RSS
**592 MiB**. Exit 0, no crash, timeout, sanitizer memory error or resource runaway.
The cov/ft values are libFuzzer instrumentation counters, not line-coverage
percentages. The target uses actual BDF/gzip registry decoding, source validation
and writing under small budgets; it does not fuzz unimplemented formats.

Earlier runs are disclosed: an initial 611-second, 1,543,781-execution run failed
only during LeakSanitizer's exit-time ptrace check in this sandbox, emitting an
empty artifact. No parser panic was reported. A subsequent 611-second run with
leak detection disabled passed (1,541,889 executions), then the final code was
rebuilt and rerun as above. Address sanitizer stays enabled. No kernel/security
settings changed; these runs do **not** certify absence of memory leaks.

Exact command and budgets: `fuzz/README.md`. Nightly 1.101.0-nightly
(c36f14571, 2026-10-01), cargo-fuzz 0.13.2, libfuzzer-sys 0.4.13.

## Decisions, limitations and follow-on integration

1. SPEC/Python wins where the catalogue parser differs: UTF-8 rather than Latin-1,
   later duplicate wins rather than first, and absent glyph metrics stay absent
2. Core source duplicates remain inspectable. The compatibility facade and SPEC
   consumers must filter to `font.glyph_id(cp) == id`, then append unencoded glyphs
3. The core needs a rectangular bitmap. Raw short/long/extra/missing/dirty rows
   remain preserved while the core view is normalized; these notes are separate
   from the exact `bdf.parse.*` warning subset
4. Invalid hex source rows remain writable verbatim but have zero placeholder
   rows in the core view. **Call `bdf::validate_bitmap` before claiming a drawable
   glyph.** W1.3 PCF should use source rows where its own specified lenient behavior
   differs, not silently treat these placeholders as validated pixels
5. Source-provenance layout and semantic-edit reconciliation are documented in
   `docs/formats/bdf.md`. Ordinary fields always serialize from actual semantics;
   unchanged source row spelling is the only raw-raster reuse
6. Source charset codes are retained without remapping or requiring CJK tables.
   Exact Unicode-to-CJK conversion requires `cjk-charsets`; no approximate fallback
   is substituted. ENCODING remains signed-32 as SPEC mandates, including for
   charsets whose theoretical raw codes can exceed that range
7. BDF represents one strike. Extra aliases expand to records with an identity-
   loss note; sequences, unsupported model fields and explicit Gray8 thresholding
   are reported. Strict checks combined read/write loss before returning assets
8. Fresh wire fields with embedded line breaks or out-of-range required integers
   are rejected by the core writer. The full W1.5 compatibility facade's arbitrary
   transient editing API and full cross-language operation runner are not claimed
9. `ReadContext` handles gzip before detection. W1.3 should enable `gzip` for
   its PCF feature and register actual hooks; no PCF reader/writer exists here.
   Direct `bdf::read` consumes uncompressed bytes. Nested gzip is explicitly refused
10. CLI info and single-asset BDF conversion work. Other formats, general sidecar
    persistence, batch, render, variants and language bindings remain their own
    work items; source prototypes are not advertised as completed codecs
