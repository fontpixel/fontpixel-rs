# W4.4 BMFont / SFD / Kbits implementation evidence

Recorded 2026-10-04. This covers the W4.4 implementation and focused checks.
Coordinated long fuzzing, five-round performance measurements and full-workspace
gates are owned by the parent task; this report does not claim those have passed.

## Implementation and fidelity

- BMFont reads and writes AngelCode text, XML and binary v3 descriptors with
  multi-page PNG. Page paths resolve through the scoped resource interface.
  Shelf packing is deterministic. Gray8 channel selection, outline/color
  reduction, PNG metadata omission and explicit monochrome thresholding are
  documented in `docs/formats/bmfont.md`; differences receive loss diagnostics.
  Native ordered info/common/page/kerning properties preserve source provenance;
  packing and channel changes are reported. Baseline conversion uses common.base.
- SFD reads all bitmap strikes at depths 1/2/4/8, original ASCII85 decoding,
  signed bearings, Unicode identities and non-variation aliases. Native depth
  2/4 is preserved when samples fit that quantization. Outline advances are
  retained separately from strike advances. Outline instructions/geometry are
  reported as omitted; bitmap composite references fail without partial output.
  The writer emits bitmap-only identity stubs, single-line ASCII names, correct
  UnicodeFull encoding capacity and no timestamps.
- Kbits reads and writes the legacy KBnPbits version-1 layout, exact Gray8,
  signed metrics, Java modified UTF-8 including encoded NUL and supplementary
  characters, native numeric names, and negative source codes. Ragged rows are
  padded with a diagnostic. Unencoded/legacy glyphs without a native identity
  fail explicitly instead of being dropped.
- All successful writers reread their output with the same individual resource
  limits and the remaining aggregate allowance, then audit every font/glyph
  metric, name, charset, property, source format, stable slot, alias, Unicode
  sequence and bitmap. Differences are reported. Invalid representability
  failures retain a fatal report and omission entries for every source glyph
  and code; resource-limit failures retain their original typed error.
- Allocation accounting includes source models and deleted slots, recursive
  metadata bounded to depth 64, output buffers, reread models, PNG scratch,
  per-strike identity clones and diagnostic asset names. PNG text/ICC data is
  skipped without decompression. The implementation does not invoke tools or
  clone complete fonts during writing; fixture/benchmark setup may clone once.

## Independent crosschecks

[w4.4-crosscheck.json](w4.4-crosscheck.json) records 11 groups, tool versions,
the final CLI binary hash and hashes of all generated artifacts. Reproduction:

```sh
../local-work/oracles/bin/python tests/crosscheck/w44.py \
  --binary ../local-work/target-w44/debug/fontpixel \
  --output-dir ../local-work/w44-crosscheck-freeze \
  --jar ../local-work/w44-oracles/BitsNPicas.jar \
  --fontforge-root ../local-work/fontforge-oracle \
  --source ../samples/tong-pixel-sans/TongPixelSans14Small-Latin.bdf
```

The output directory must not already exist. All tools are test-only black boxes.

- BMFont: monobit 0.54 writes independent text/XML/binary fixtures that Rust
  reads. It also reads Rust output. Raster samples, x bearing and advances agree;
  its reader ignores common.base and derives baseline from raster height. The
  script explicitly asserts the resulting exact y difference, rather than
  hiding it. The reverse direction agrees on complete raster-space metrics.
- SFD/Kbits: Bits'N'Picas 2.2.2 independently reads Rust output and emits Kbits;
  Rust reads that output. A separate field-oriented Python Kbits reader and the
  frozen MIT catalogue KBITX/BDF readers compare every glyph's code, dimensions,
  signed bounds, advance and pixels. Both the original three-glyph fixture and
  the supplied 3,645-glyph Tong small Latin source pass.
- SFD: Python's standard ASCII85 encoder plus an independent bit packer creates
  nonzero depth-2/4/8 fixtures; all expected Gray8 samples and metrics agree.
  The official Ubuntu FontForge 20230101 executable reads/resaves Rust SFD and
  exports BDF; Rust and the catalogue agree on the entire original fixture,
  including U+20000. Reverse FontForge BDF-to-SFD also passes on a BMP fixture.
  FontForge's BDF importer is UCS-2, so no non-BMP reverse claim is made.
- FontForge and Bits'N'Picas both confirm that the actual BDFChar field order is
  xmin,xmax,ymin,ymax, differing from the prose order in the public SFD document.
  The original negative-bearing fixture distinguishes these interpretations.

## Fuzz and performance handoff

`fuzz/seed_w44.py` emits 12 original deterministic seeds in
`../local-work/w44-fuzz-seeds/{bmfont,sfd,kbits}`; hashes are recorded in
[w4.4-seeds.json](w4.4-seeds.json). BMFont's fuzz envelope is a little-endian u32
descriptor length, descriptor bytes and a PNG resource payload. The resolver
supplies that payload for each page reference. Every target independently
rereads successful writer output using the original limits, and asserts full
Font/FontSet equality when no loss was reported. SFD/Kbits also assert canonical
byte stability on a second native write.

`w44_timing INPUT.bdf [LOOPS]` prints a JSON array with separate read_ns and
write_ns for each format, glyph count, serialized bytes and loop count. Setup
conversion lies outside reader timing; writer timing includes its integrity
audit. No formal timing or long fuzz campaign was performed by this worker.
The parent owns the coordinated ASAN campaigns of at least 610 seconds and
five performance rounds against the frozen manifest.

Remaining explicit format limits: BMFont v1/v2 and animated PNG are unsupported;
SFD outline geometry is omitted with loss, composite bitmaps and non-ASCII output
names fail; legacy/unencoded Kbits output requires an explicit native identity.
No monobit SFD/Kbits interoperability is claimed because it has no such handlers.
