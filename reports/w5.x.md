# W5.X — BMFont JSON and explicit raw layouts

BMFont now reads and writes Jam3 JSON descriptors with PNG pages. Raw now
supports continuous bit packing, byte-column ordering, horizontal glyph strikes
and three explicit Harlekin profiles. The original raw defaults, C64 `.64c`
prefix precedence and BMFont text/XML/binary-v3 encodings retain their behavior.
This result extends two existing families; it does not add font IDs or close
phase 5. The coordinator owns shared feature/registry/CLI integration.

## Native representation and bounds

`BmfontEncoding::Json` follows the published Jam3 schema: object-valued info and
common, ordered string pages, ordered glyph and kerning arrays, integer metrics,
boolean flags and padding/spacing arrays. The existing PNG reader, coordinate
transform, channel semantics, atlas packing and full model audit are reused.
JSON duplicate keys and unsupported value types are explicit errors. Unknown
string/integer/boolean/flat-integer-array fields retain native type provenance;
repacking omissions are reported. The JSON probe checks complete syntax and the
four required root container types without building records or font models, and
returns `Possible`. Direct codec writes enforce strict loss rejection.

`RawLayout` adds `packing`, `byte_order` and `strike_count` with unchanged default
values. Byte-aligned strikes concatenate actual pixel widths horizontally before
whole-row padding. Column-major transposes the byte matrix of each strike;
bit-order and top/bottom row order remain independent. Bit-aligned mode packs
across row and glyph boundaries and rejects incompatible stride/padding options.
Explicit counts distinguish incomplete final strikes or otherwise ambiguous tail
bits. Nonzero unused padding is reported as a repair. No raw detector is added.

Harlekin primary documentation conflicts: monobit 0.54.0's README describes
512 8×8 glyphs in one 4096×8 strike, while the Atari page linked by its raw loader
describes 256 8×8 or 8×16 glyphs. Distinct profiles preserve all three definitions:
`harlekin-iii`/`harlekin512`, `harlekin8`, and `harlekin16`. None infers charset
or recognizes arbitrary files by length. References and wire definitions are in
[raw.md](../docs/formats/raw.md) and [bmfont.md](../docs/formats/bmfont.md).

Cumulative budgets cover retained input, JSON escape/key buffers and records,
canonical model allocations, raster scratch, vector capacity and diagnostics.
Array count limits precede an excess element's deserialization. For bit-packed wire data, scratch and readback reservations use the expanded
canonical row size, including skinny cells whose internal size is up to eight
times larger than wire storage. All geometry arithmetic is checked; writer output must be readable under identical limits.
The default raw byte-copy path is retained and its one-glyph scratch buffer is
reused. Additional raw layouts write into the final output allocation without
repeatedly rebuilding an atlas. The direct raw trait reader uses the actual
`ReadContext` limits rather than an unrelated options copy.

## Validation

- 28 dedicated tests pass: 12 raw and 16 BMFont. They cover prior layouts and
  descriptor encodings, asymmetric raster fixtures, ordering and coordinates,
  all bit/row orders, partial strikes, padding and prefixes, three Harlekin
  profiles, JSON Unicode escaping/types/duplicates, exact boundaries, resource
  limits and strict glyph-metadata loss.
- Six independent feature gates pass: test, warning-denying Clippy, and
  warning-denying rustdoc for each of `raw` and `bmfont`.
- Thirteen independent crosscheck cases pass: twelve raw configurations and a
  JSON case with unsorted codes, three native atlas pages, grayscale values,
  negative bearings, non-BMP Unicode and kerning. Ten raw cases use monobit
  native writer/reader or its public Raster API. Two mixed-order/padding cases
  use an original row-string assembler and exact native wire equality.
- Original seed generation produces 26 files. Both fuzz targets exercise the
  extended read/write paths; the BMFont target also calls the JSON detector.
  Final-source short ASAN results and exact commands are in the smoke index.

Two independent-tool differences are recorded and asserted rather than patched:

1. monobit 0.54.0's raw wrapper supplies `byte_order=` to a Raster API whose
   current keyword is `order=`. Its `**kwargs` absorbs the obsolete name.
   Column-major verification therefore calls its public
   `Raster.from_bytes(order="column-major")` plus cell crops. The independent
   writer direction transposes monobit's row-order output using an original
   byte-matrix assembler. The wrapper's incorrect result is separately asserted.
2. monobit's BMFont reader ignores `common.base` and derives the baseline from
   maximum raster height. Every resulting y-offset difference is asserted as
   exactly `max_height - common.base`; all pixels, x bearings, advances and
   codepoints are compared without adjustment. The reverse writer case begins
   with explicitly authored glyph metrics instead of that normalized reader.

The three oracle source files exactly match the official monobit 0.54.0 PyPI
source archive. The shared install remains unmodified. monobit is MIT; all raster
artwork and hand-authored wire fixtures are original project-authored MIT data.
No historical artwork or incompatible implementation code is incorporated.

## Coordinator handoff

Builds use `source scripts/local-env.sh`, `CARGO_BUILD_JOBS=2` and the isolated
`$FONTPIXEL_WORK_ROOT/target-w5x`; short fuzz uses `target-w5x-fuzz`. Crosscheck
fixtures are reproducible under `$FONTPIXEL_WORK_ROOT/w5x-crosscheck-final2`.
The extended `raw` and `bmfont` fuzz targets use their existing `raw-only` and
`bmfont-only` feature switches. Production source is bound by the freeze index.

Formal 610-second ASAN, five quiet release-performance repetitions and combined
repository gates remain coordinator work. The in-memory timing interfaces are:

```text
w5x_timing bench raw|bmfont INPUT CONFIG_JSON LOOPS
python tests/crosscheck/w5x.py --bench raw|bmfont --file INPUT --config CONFIG_JSON --count LOOPS
```

Use `{"width":9,"height":3,"count":7,"packing":"bit"}` for `bits9/source.raw`,
`{"width":16,"height":5,"count":6,"order":"column"}` for `columns16/source.raw`,
`{"width":8,"height":8,"count":512,"strike_count":512}` for
`harlekin512/source.raw`, and
`{"encoding":"json","page_width":4,"page_height":4}` for `bmfont/source.fnt`.
`legacy/source.raw` uses `{"width":8,"height":8,"count":8}` and keeps the old
layout available for comparison. All adapters preload filesystem inputs before
timing; Python BMFont uses in-memory Location/Stream resources. Column-order
Python timing uses the functional Raster API and explicit writer transpose.
One-iteration adapter checks establish functionality only, not performance.

Requested worker configuration remains `gpt-6-astra`, `xhigh`; fast-mode status
is not independently observable. No subagent, Git mutation, reference/sample
edit, shared source edit or whole-repository build was performed.
