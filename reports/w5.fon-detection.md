## Native evidence and implementation

Microsoft's [archived NE description](https://github.com/qb40/exe-format) defines header-relative resource offsets, resource-type directories and the Windows target byte at `0x36`; its [resource types](https://learn.microsoft.com/en-us/windows/win32/menurc/resource-types) assign FONT `8` and FONTDIR `7`. Existing OS/2 GPI support documents and validates its different native resource directory. Detection now uses the existing bounded Windows directory traversal and verifies FNT resource headers. It allocates only directory bookkeeping/diagnostics, never glyph models. Both the public default-limits probe and registry context-limited probe reject incomplete signatures, absent FONT resources, malformed offsets, invalid PE traversal, or exhausted metadata budgets.

A real Windows FONT NE/PE remains Certain. An OS/2-targeted NE that nevertheless contains valid Windows FONT resources is Possible, preserving ambiguity rather than letting one family override contradictory evidence. Filename extensions do not participate. Explicit FON reading/writing is unchanged. Tests independently assemble Windows NE, PE32 and PE32+ resource directories around original glyphs, include bare NE/PE, and verify that native GPI NE is not claimed by FON and genuine Windows NE is not handed to GPI.

C detection keeps a cheap marker/initializer-shape filter before token allocation; ordinary large BDF/HEX input does not require C lexical analysis. Candidate source uses the existing lexer and declaration parser under the context's retained-input and aggregate/table budgets. Actual native struct/array declarations supply evidence; comments, strings and arbitrary directives do not. Generic `fontpixel-c` and native `fontpixel-u8x8` comments require a real byte array. A genuine quoted font8x8 include remains Possible without resolving any resource. Binary LVGL recognition remains unchanged. No compiler, preprocessor, include loader or native font decoder runs during detection.

The initial positive-writer coverage found that the existing U8x8 writer may use a custom symbol plus its `fontpixel-u8x8` comment. That real marker/declaration combination is now covered along with Generic, GFX, U8g2, LVGL, NetBSD and U8glib output. Readers, writers, GPI sources, shared registry/resources and transport files were not edited.
